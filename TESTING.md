# Default verification and coverage

Run `bash scripts/check.sh` before review. CI runs the same command on every PR and
main push. It needs JDK 21, Android SDK 37, Python 3 and Go 1.26. It does not require
an attached phone, login, customer key, or reachable provider API.

The wrapper explicitly sets `GMC_VERIFY=true`: local customer-key properties are
ignored and debug uses the synthetic mock configuration. Both debug and R8-minified
release APKs are built, but not installed, published, or promoted as release artefacts.
The release build verifies compilation/shrinking, not installed release behaviour.

## What runs by default

- All JVM and Robolectric tests, including Compose rendering, navigation, WorkManager,
  credential handling, repository validation, cache and updater tests.
- AGP/JaCoCo XML and HTML coverage, with reviewed floors enforced by `verifyCoverage`.
  Conventional `:app:check` also depends on that gate; the wrapper additionally runs
  Go, Python, dependency notices and both APK builds.
- Android lint, dependency notice validation, all Python tooling tests, Go mockserver
  handler/fixture tests with the race detector, and `go vet`.
- CI retains JUnit XML, test HTML, coverage and lint reports for 14 days, including
  failure runs. Missing or below-floor coverage fails verification.

## Reading coverage honestly

Open `app/build/reports/coverage/test/debug/index.html`; the machine-readable report
is `report.xml` in that directory. Floors live in `scripts/coverage-baseline.json`.
Do not lower them to make a patch green without an explicit review of why coverage
changed. Raise them as behaviour coverage grows. They are regression alarms, not
proof that a feature works or targets for meaningless assertions.

The first audit report around 10.8% lines omitted Robolectric sandbox-loaded classes.
The JaCoCo plugin and `includeNoLocationClasses` configuration correct that measurement.
The whole-source total deliberately still includes Compose and generated classes;
we do not discard the UI merely to improve the headline. Compose is testable with
Robolectric and already has tests here. Package figures combine orchestration and
rendering, so inspect individual source files before concluding a ViewModel is untested.

## Behaviour inventory

The suite covers the JVM and Robolectric behaviour listed below. Whole-source coverage
figures, including per-file line and branch coverage, are generated by the run itself
into `app/build/reports/coverage/test/debug/` rather than quoted here, so they cannot
drift out of date. The four screen coordinators (Home, Schedule, Messages and Account
ViewModels) have their own coverage floors, so unrelated tests cannot hide a large
regression in any one of them. Coverage figures are execution measures, not claims
that every race is tested.

| Area | Automated evidence | Remaining boundary |
| --- | --- | --- |
| Authentication | Bearer freshness, refresh, repeated 401, logout races, contact lookup fallback, login claims and errors on API 28/35 | Actual browser/loopback callback, provider authorisation, MFA and real account availability |
| Home | Independent module outcomes, targeted retry, in-flight sibling preservation, cache-write completeness, auth error precedence and recovery | Full-refresh versus targeted-retry overlap; real slow-service behaviour |
| Schedule/history | Inclusive window clamping, partial extension failure, cache retention, term batching/completion and rendering | Live term metadata validity and latency |
| Messages/compose | Received versus sent caching, cancelled tab load, read-state targeting, empty refresh, send outcome/trim/duplicate guard, cancellation and restored drafts | Remote delivery/read persistence and full draft lifecycle on hardware |
| Account/secondary screens | Complete and partial account refresh, cached fallback, pupils/reports retry, billing precedence, activity grouping, initial notification preferences | Concurrent Account refresh ordering; settings setters with actual OS scheduling |
| Notifications | Existing worker, permission, account ownership, deferred delivery, reminder and intent integration tests | OEM background restrictions, Doze and real notification delivery |
| Updates | Manifest parsing, integrity, download cancellation, installer permission-return and version checks | Actual package installer, signer acceptance and provider/CDN availability |
| Persistence | Snapshot round-trip, static owner isolation, signed-out behaviour and clearing | Corrupt/schema-mismatch files, I/O faults, account transition during delayed writes and disconnect/write races |
| Tooling/mock | Dependency-notice tooling, coverage gate failure cases, mock HTTP envelopes and fixtures | Mock payload success does not prove the provider implements the same contract |

This is a source-wide coverage sweep, not a claim of exhaustive state-space coverage.
The remaining concurrency and persistence cases above are concrete follow-up work,
not silently counted as passing. Existing helper/worker tests remain valuable, but
they cannot substitute for tests of the screen coordinating those helpers.

## Regression fixes demonstrated by this sweep

New tests failed before fixing login setup exceptions leaving a loading spinner,
cancelled sends being reported as errors, and a Home timeout hiding an authentication
failure from a different module. Preserve those failure cases when refactoring.

## OAuth callback and session activation

Deterministic loopback and PKCE behaviour is covered by `LoopbackGapTest` (valid
callback with exact single token exchange, redirect and PKCE-verifier agreement,
wrong/missing state rejection, provider cancellation, a stray favicon request not
consuming the real callback, and failed/malformed token-exchange responses) together
with `LoginAndComposeTest` (cancelled browser result, transport failure ending loading
with a retryable error, cancellation staying cancellation, malformed identity, and a
lookup rejection offering retry rather than a false no-account).

These do not exercise the real system browser, multi-factor prompts, or the provider's
five-minute callback deadline, and the signed-out to session-activation path is driven
with a mocked resolution rather than a full integration. Those remain manual,
provider-dependent checks on an authorised test account/device - see below - and must
not be run with a real parent session or real messages as fixtures.

## Physical-device and live checks

Do not use a signed-in parent session or real messages as CI fixtures. Keep hardware
smoke testing separate and use a dedicated synthetic installation when practical.
Before a release, exercise app startup, browser return, navigation/back, process death,
notification permission, unknown-app installation return, and minified APK startup.
Mock tests and a successful build are not a substitute for these checks. Do not clear
or overwrite the user's existing diagnostic installation to make automated tests pass.

Coverage setup follows the [Android coverage reporting documentation](https://developer.android.com/studio/test/coverage-report).
